# What Is Life 2 — Canonical Documentation

Status: canonical index  
Established: 2026-08-02  
Revised: 2026-08-04

This directory is the durable project memory for What Is Life 2. A decision is
not canonical merely because it appeared in a conversation or mock-up. It must
be represented here and merged to the repository's `main` branch.

## Authority order

When documents overlap, read them in this order:

1. [Decision log](DECISIONS.md) — settled corrections and non-negotiable
   distinctions.
2. [Product north star](PRODUCT_NORTH_STAR.md) — the player fantasy and the
   scope guardrail that prevents technical rigor from replacing play.
3. [Core fun-loop design](CORE_FUN_LOOP_DESIGN.md) — the player-experience
   authority for layered living systems, biological language, causal
   comprehension, revision, attachment, and the proof gate before expansion.
4. [First synthetic cell design](FIRST_SYNTHETIC_CELL_DESIGN.md) — the concrete
   vertical-slice bridge from the existing Intake, Transfer, Buffer, policy,
   Field, qualification, and engineering-memory substrate to the first
   player-facing organism.
5. [Product outline](PRODUCT_OUTLINE.md) — the broader product promise,
   surfaces, and scientific posture.
6. [Automation and contract authority](AUTOMATION_AND_CONTRACTS.md) — the
   authoritative implementation model for local policy, contract content,
   qualification, persistence, and engineering records.
7. [Atlas and mechanics contract](ATLAS_AND_MECHANICS.md) — regimes,
   quantities, instruments, experiments, objectives, and validation.
8. [Form and reality-of-play model](FORM_AND_PLAY_MODEL.md) — exact meaning of
   the steerable or programmable Form, resource flow, abilities, click targets,
   and causal model. A Form is not the complete cell or generator.
9. [Number 2 mock-up pseudocode](NUMBER_2_MOCKUP_PSEUDOCODE.md) — visual and
   implementation contract for every retained mock-up.
10. [Platform and delivery](PLATFORM_AND_DELIVERY.md) — remote, static-web, and
    macOS runtime and packaging boundaries.
11. [Current codebase state](CODEBASE_STATE.md) — dated implementation truth and
    known mismatches.
12. [Continuous development loop](DEVELOPMENT_LOOP.md) — binding milestone,
    publication, and panel-review cycle.
13. [Milestone ledger](MILESTONES.md) — the sole authority for the one active
    implementation milestone and its evidence.
14. [Working rules](WORKING_RULES.md) — contributor process, including the
    absolute no-TDD rule.

The north star and fun-loop documents govern what the player should understand
and feel. The automation and mechanics documents govern how causal state and
evidence work. The first-cell specification governs the first vertical slice.
`MILESTONES.md` alone says which packet is active.

If a visual label conflicts with a mechanics document, the visual composition
remains and the label does not. If a target document conflicts with the dated
codebase state, the former describes the destination and the latter describes
what exists today. A biological player label may simplify an internal record,
but it may not imply a mechanic the authoritative core does not own.

## Active implementation milestone

[The milestone ledger](MILESTONES.md) is the sole authority for what is active
now. The first-cell specification does not silently interrupt the active
engineering-memory packet. Before implementation begins, the ledger must select
or incorporate a bounded first-cell packet and preserve any lower transition
boundary on which rapid revision depends.

Implementation sequences in the product, mechanics, mock-up, and dated
codebase documents are dependency backlogs; they do not compete with the one
selected milestone.

After a milestone is implemented, inspected, validated, and published, the
science, game-design, and engine panel reviews its evidence and selects the next
bounded milestone.

## Editing rule

Change the narrowest owning document. Add a dated decision when a settled rule
changes. Do not edit a mock-up to smuggle in a new mechanic, do not infer a
scientific claim from an attractive visualization, and do not add a biological
noun that implies absent causal behavior.

Player-facing work must answer:

- which layer of the living system is being manipulated;
- what player question the mechanic answers;
- what first visible consequence it creates;
- what informative failure exposes its relationship;
- how the player revises it;
- what exact authoritative state supports every visual and summary.
